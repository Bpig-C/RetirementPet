## 1. 本项目采用 MIT 的范围

RetirementPet 原创源代码和项目文档采用 MIT License。MIT 允许任何人使用、复制、
修改、合并、发布、分发、再许可和销售这些内容，也允许商业使用、公司内部使用和
闭源衍生；条件是分发本项目代码或其实质部分时保留版权声明和 MIT 许可文本。

MIT 不要求修改者公开源代码，不要求把修改回馈上游，也不保证贡献一定被官方仓库
接受。官方仓库的名称、发布渠道、维护者权限、分支保护和内容审核仍由维护者管理。
许可证授权与“能否直接推送 `main`”是两件独立的事。

## 2. 不自动纳入 MIT 的内容

根目录 MIT 不会覆盖已经明确声明另一许可的内容，尤其包括以下几类。

- `.petpack` 内嵌的 `legal/` 文件以及对应图片、声音、字体和文字；
- `character-work/` 中带有独立来源或许可声明的角色资产；
- 测试夹具中用于验证许可字段的独立示例内容；
- PySide6、Qt、Python、PyInstaller 等第三方组件。

项目图标等仓库级原创资产的明确映射见[资产许可表](../assets/LICENSE.md)。没有进入
该表、根许可证或包内许可闭包的媒体文件，不应被视为已经获得公开再分发授权。

现有官方退休猫 Revision 的包内许可仍是“保留所有权利，允许随 RetirementPet
再分发”；半写实预览包也保留其现有项目范围许可。它们是已经发布并按摘要冻结的
Revision，不能只改根目录 `LICENSE` 就静默换证。若未来希望某个角色使用 MIT、
CC BY 4.0 或 CC0，应由权利人明确授权，提升包版本，更新 `legal_file_ref`、来源记录
和内容摘要，再走新的构建与审核流程。

这两份现有自定义文本没有完整说明公众修改、商业再分发和 fork 项目的边界，下载者
不应把它们理解成通用开放内容许可证。公开角色库应尽快发布权利人明确授权的新
Revision，旧包仅按其原文范围保留兼容和审计用途。

## 3. 常见软件许可证的区别

| 类型 | 典型许可证 | 下游能闭源吗 | 分发修改时的主要义务 | 对本项目的维护影响 |
|---|---|---|---|---|
| 宽松 | MIT | 可以 | 保留版权与许可文本 | 采用最简单，但不能强制回馈修改 |
| 宽松 | BSD-3-Clause | 可以 | 与 MIT 类似，另有不得借作者名义背书条款 | 义务仍轻；没有 Apache 式明确专利条款 |
| 宽松+专利 | Apache-2.0 | 可以 | 保留许可证、标注修改；上游提供 NOTICE 时按条款处理；含明确专利授权和专利诉讼终止条款 | 企业专利边界更清楚，发行材料略多 |
| 文件级弱互惠 | MPL-2.0 | 部分可以 | MPL Covered Software 文件继续受 MPL 管理，较大作品的其他文件可用别的许可证 | 可要求受覆盖文件开放，但混合许可治理更复杂 |
| 库级弱互惠 | LGPL-3.0 | 满足组合与分发条件时可以 | 提供适用库及修改的对应源码、许可告知和调试所需信息，并允许用户替换或重新链接 | 适合库；本项目使用 PySide6/Qt 时需单独满足此类义务 |
| 强互惠 | GPL-3.0 | 分发衍生程序时通常不可以闭源 | 整个受覆盖的分发衍生作品提供对应源码并沿用 GPL 权利 | 能保证公开改进，但限制闭源集成与部分商业采用 |
| 网络强互惠 | AGPL-3.0 | 网络使用也受约束 | 用户与 AGPL 程序的修改版本远程交互时，还要向其提供对应源码 | 适合网络服务；当前本地桌宠没有明显收益 |

MIT 是当前桌面工具阶段的合理默认。接入门槛低、允许个人和企业自行打包，也方便
以后把引擎用于其他本地应用。代价是他人可以做闭源分支而不回馈。如果未来项目更
重视“所有公开发行的改进必须开源”，应把换证作为单独治理决策；不能假设已经收到
的第三方贡献可以由维护者单方面重新许可。

## 4. 美术、声音和角色内容

软件许可证不一定适合内容资产。角色包 PR 应逐资产选择并证明适用许可，例如以下
几种。

- `CC0-1.0` 尽可能放弃著作权限制，复用最宽；
- `CC-BY-4.0` 允许修改和商业再分发，但必须按要求署名；
- `CC-BY-SA-4.0` 除署名外，改编内容还要按同一许可分享；
- 定制书面授权必须明确是否允许修改、公开仓库、安装包和商业再分发。

除 CC0 这类特殊工具外，Creative Commons 通常不用于程序代码，也没有 Apache-2.0
式的软件专利条款。不要把“可在本地使用”当成“可随公开安装包再
分发”。Harry Potter、罗小黑等现有 IP 即使由贡献者重新绘制，也可能涉及著作权、
商标或不正当竞争等权利；没有可核查授权时只能留在用户本地，不能进入官方仓库。

## 5. Pull Request 的许可关系

项目暂不要求单独签署 CLA。提交 PR 即表示贡献者确认以下事项。

1. 有权提交相应代码、文档和内容；
2. 原创代码与文档自提交时起按本项目 MIT 条款许可给项目及所有接收者；
3. 独立许可的内容资产已经逐项披露作者、来源、许可、署名和再分发范围；
4. 不会用 schema、hash、AI 生成声明或“仅供学习”代替真实授权。

维护者审核和合并不替代贡献者的权利保证；发现来源或授权不一致时，可以拒绝、
撤回或从后续版本中移除内容，同时保留原始审计事实。

## 6. 发布二进制时的额外义务

MIT 只解决项目原创部分。Windows onedir 包还会分发 Python、PySide6、Qt、
PyInstaller bootloader 及它们携带的第三方库。每次公开二进制发行前必须根据实际
artifact 生成组件清单，随包提供适用许可和署名，并满足 LGPL 等许可证对对应源码、
用户替换/重新链接和修改说明的要求。当前入口见[第三方声明](../THIRD_PARTY_NOTICES.md)。

没有完成这一步的历史本机构建只能作为内部 Alpha 证据，不能因为仓库改成 MIT 就
直接上传到公开 Release。
