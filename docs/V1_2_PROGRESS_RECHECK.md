## 两项补充返工

### CR-P03 / P1：连续切换会永久丢失较早的激活审计

位置：`lifecycle.py::record_activation_committed`、
`switcher.py::_record_activation` 与 `_reconcile_activation_journal`。

复现：第一次切换的 ACTIVE 已提交，注入审计写入返回 False；恢复审计写入，
第二次切换成功；重新构造 ActiveSelectionStore。两次切换均确认成功，当前
generation 为 2，但事件历史仅含 `[2]`，预期应为 `[1, 2]`。当前重启补记只查看
最后 ACTIVE，已被覆盖的 generation 1 无法找回。

要求：保留每次已确认激活的可恢复待记事实，重试/重启时按事实补记，而不仅从
当前槽位推断；可采用与选择提交一致的持久待办事件等方案，实现由执行者决定。
继续保持 ACTIVE 为当前选择权威，审计失败不得反转已确认切换。补“失败一次后
继续切换”“连续多次失败后恢复”“重启幂等”测试。此项属于原 CR-P02 的完整性
收尾，不能宣称追加历史已经闭环。

### CR-A05 / P2：恢复成功返回值没有反映重开失败

位置：`todo/service.py::restore_from_backup` 与 `_reacquire_after_restore`。

复现：备份有效，数据库替换和 fsync 都成功，仅让 TaskRepository 重开抛出
TaskStoreUnavailable。恢复接口正常返回 RestoreResult，但 service.degraded
为 True，任务查询为空，而磁盘实际有 1 项。禁写保全是正确的，普通返回结果
却不能让调用方分辨“全部可用”和“数据已恢复、待办仍不可用”。

要求：明确返回部分成功/不可用状态，或抛带发布阶段信息的稳定异常；不要误称
原库未变。V12-05 界面须显示真实恢复结果与后续操作。补仅重开失败的独立测试，
不能只在同时注入 fsync 失败时验证禁写。已故障服务再次恢复的 AttributeError
与 `focus_task()` 读契约问题一并规范，最晚在 05 接入前完成。
