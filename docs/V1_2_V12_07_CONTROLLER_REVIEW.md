## L07-01（P1）：重启续删没有重新检查当前与恢复依据

位置：`lifecycle.py::request_uninstall/_recover_pending_deletes`（1385/1428
行起）、角色页切换入口。新续删直接调用 `uninstall_revision(rk)`，没有保护 guard。

独立合成应用复现，使用真实 Windows 文件句柄占用、真实切换和完整应用重建：

1. 安装 minimal-static，打开包文件句柄；请求删除返回 pending_delete。
2. 关闭句柄。该待删除版本仍可以通过 `_switch_character` 正常激活。
3. 情形 A：保持它为 active，关闭并重新构建 PetApplication。该版本目录行和
   包文件均被删除，应用丢失原选择并回退。
4. 情形 B：激活后完成健康检查点，再切回官方角色，令它成为 last_known_good；
   重启后同样被删除，last_known_good 槽位还指向已删除的 Revision。

要求：执行删除时按最新持久化事实重新检查 active、last_known_good 以及既有
恢复引用；不能只依赖用户最初点击时的 guard。明确待删除版本再次被选中时是拒绝
激活、撤销待删还是推迟删除，保证状态闭环；实现方案由执行者选择。补上述两种
真实重启场景及未使用版本正常续删对照。也核对媒体已消失/中断重试时目录行、
pending 行、事件的一致性，不能遗留一个仍可选但没有媒体的条目。

## L07-03（P2）：缩略图先全尺寸解码，缓存键未包含角色身份

位置：`ui/panel/pages.py::_load_thumbnail`（574 行起）。

代码先 `QImage.fromData(data)`，再 `image.scaled(96,96)`；96px 是最终缩放
尺寸，并非解码上限。8 MiB 限制是压缩 PNG 字节数，不能作为解码内存限制。
校验器单图允许至 4096×4096 像素，因此有效高压缩图也可能在 UI 线程先分配
约 64 MiB 像素缓冲，再缩成小图。执行方“不全尺寸解码、解码上限96px”的
报告与代码不符；现有测试仅验证最终 pixmap/缓存条目数量。

此外缓存 key 仅为 `str(entry.revision_key)`。同一包多个角色声明不同
thumbnail_asset 时，首次查看 A 后再查看 B 会直接命中 A 的图。这是代码路径
可确定的问题，本轮未把它写成已经运行过的多角色像素探针。

要求：使用有实际资源界限的读取/解码策略，明确所用图片格式下是否仍需原尺寸
中间缓冲；必要时限制缩略图专用尺寸并给出占位反馈。缓存按角色/变体或实际
缩略图资产身份区分，同时保留总量上限。补一个压缩小而像素大的合法输入和
同 Revision 两角色不同缩略图的验证；报告区分读取、解码、缩放和缓存上限。
